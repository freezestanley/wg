# webgen 页面设计指南

> 目的：为 `webgen` agent 提供统一的页面设计、前端审美、动效选型与 skill 协同流程。该文档用于指导 `webgen` 在生成或迭代网页时，如何稳定调用已安装能力、遵循统一约束，并输出可运行、可预览、可交付的页面结果。

## 0. 使用方式

- 需要快速判断任务方向时，先看：`docs/webgen-design-cheatsheet.md`
- 需要完整规则、约束、流程、选型依据时，再看本文
- 默认顺序：`AGENTS.md` → `docs/webgen-design-cheatsheet.md` → `docs/webgen-design-guide.md`

### 0.1 规则优先级

当多份规则出现交叉或冲突时，按以下优先级执行：
1. `AGENTS.md` 硬约束
2. 当前项目自己的约束、品牌规范、组件规范、接口约束
3. 本文档 `docs/webgen-design-guide.md`
4. 已安装 skill 的建议与偏好

执行原则：
- 本文档只定义 `webgen` 的默认增量规则，不覆盖 `AGENTS.md`
- skill 内部若与 `webgen` 既有约束冲突，以 `AGENTS.md` 和本指南为准
- 项目已存在品牌 / 设计系统时，优先延续项目体系，不为追求“高级感”强行改风格

## 1. 文档定位

这份文档不是灵感清单，而是 `webgen` 的默认设计操作系统。

适用范围：
- 新页面生成
- 现有页面改版
- Landing Page / 官网 / 活动页
- 仪表盘 / SaaS / 工具后台
- 页面动效增强
- 品牌感、质感、审美升级

核心目标：
- 让页面结果稳定、统一、可落地
- 让设计判断不再靠临场拍脑袋
- 让 skill 分工、技术选型、交付检查可复用
- 减少“AI 模板味”“乱堆特效”“结构松散”的低质量输出

## 2. 最高优先级约束

这部分是默认硬规则。若用户没有明确提出相反要求，`webgen` 必须遵循。

### 2.1 先方案，后编码

- 必须先给出页面方案，再进入实现。
- 方案至少说明：
  - 页面目标
  - 主要板块
  - 风格方向
  - 配色 / 字体方向
  - 素材 / 接口策略
  - PC / Pad / H5 适配策略
- 用户未明确确认前，不进入页面业务代码实现。

方案默认输出模板：
1. 页面类型 / 目标
2. 目标用户 / 使用场景
3. 主要板块与信息层级
4. 风格方向与设计拨盘：`DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`
5. 配色 / 字体 / 图标方向
6. 素材 / 文案 / 接口来源与缺口
7. 技术实现与依赖策略
8. 状态设计：`Loading / Empty / Error / Active Feedback`
9. 响应式策略：断点、Pad 横竖屏、H5 首屏优先级、hover 替代
10. 风险、假设、待确认项

### 2.2 先可运行，再精修

默认推进顺序：
1. 先搭结构
2. 再定层级与视觉
3. 再补状态与交互
4. 再加动效
5. 再做响应式细化
6. 最后收口性能与细节

### 2.3 默认技术与实现立场

- 默认优先原生 HTML / CSS / JS。
- 若已有项目使用 React / Next / Vite，则优先延续，不轻易换栈。
- 页面设计必须能真实落地为可运行代码，不输出纯概念稿。
- 视觉表达必须服务页面目标，不为炫技牺牲信息传达。

### 2.4 默认图标规则

- 默认只使用 **Lucide**。
- 不混用多套图标库。
- 若 Lucide 无法满足，再说明原因后扩库。
- 图标线宽、圆角、视觉密度必须统一。

> 注：新安装的 `design-taste-frontend` skill 内部推荐 `Phosphor / Radix`，但对 `webgen` 来说，默认仍以 Lucide 为先；除非用户明确指定，或项目现有体系已固定使用其他图标库。

### 2.5 动效库选择规则

根据场景选最合适方案，不无原则混用：
- `Anime.js`
- `Motion`
- `GSAP`
- `Three.js`

所有动效必须服从：
- 可读性
- 性能
- 响应式适配
- 交互清晰度
- 设备兼容与降级策略

### 2.6 默认资源策略

默认浏览器侧资源优先使用以下 CDN：
- Axios：`https://cdn.jsdelivr.net/npm/axios/dist/axios.min.js`
- Tailwind CSS：`https://cdn.tailwindcss.com`
- Lucide：`https://unpkg.com/lucide@latest`
- Web Awesome CSS：`https://ka-f.webawesome.com/webawesome@3.8.0/styles/webawesome.css`
- Web Awesome loader：`https://ka-f.webawesome.com/webawesome@3.8.0/webawesome.loader.js`
- anime.js：`https://cdn.jsdelivr.net.cn/npm/animejs/dist/bundles/anime.umd.min.js`

使用原则：
- 优先延续项目现有技术栈与资源体系
- 新建页面若无既有约束，先按以上默认资源策略落地
- 偏离默认资源策略时，要能说明是因为项目既有体系、性能、合规或用户指定，而不是随意换源或扩库

### 2.7 配图与图片素材策略

适用于需要真实配图、用户不提供素材、且明确允许去线上找图的场景。

- 设计时优先找真实图，找不到再用 SVG 占位
- 用户提供图片时优先用用户素材
- 只有在用户明确同意后，才去线上找可商用免授权图
- 默认图库源：
  - `unsplash.com`
  - `pexels.com`
  - `pixabay.com`
  - `shopify.com/stock-photos`
- 获图优先顺序：
  1. 用户提供图片或 URL
  2. 图站稳定 CDN 热链 URL
  3. 搜索页辅助获取候选
  4. 实在找不到再退化为 SVG 占位
- 每个图片 URL 上线前都必须校验可用，并确认页面预览无破图
- 所有选用图的 URL、用途、状态都要写入 `ASSETS.md`
- 若交付物依赖外网热链，交付时要说明；若要求自托管，再下载进项目资产目录并改引用

## 3. 设计总原则

### 3.1 页面设计不是“好看”，而是信息与行为设计

页面设计必须同时负责：
- 信息层级
- 可读性
- 交互反馈
- 响应式布局
- 视觉秩序
- 性能体验
- 目标转化或任务完成率

### 3.2 高级感不靠堆元素

页面需要“高级感”时，优先依靠：
- 留白
- 比例
- 排版
- 节奏
- 色彩克制
- 材质细节
- 有节制的动效

不是依靠：
- 泛滥渐变
- 泛滥阴影
- 泛滥毛玻璃
- 大量装饰图标
- 无意义数据卡片
- 夸张炫光

### 3.3 先确定页面角色，再决定视觉强度

常见页面角色：
- 转化型：强调清晰、可信、低阻力
- 品牌型：强调记忆点、气质、统一世界观
- 产品型：强调结构、反馈、信息效率
- 叙事型：强调节奏、滚动、镜头感
- 工具型：强调秩序、密度、状态可读性

不同角色决定：
- 是否允许强视觉
- 是否需要复杂动效
- 是否强调沉浸感
- 信息密度应高还是低

## 4. 基于 design-taste-frontend 的增强规则

以下内容吸收了 `design-taste-frontend` skill 的核心设计方法，并结合 `webgen` 现有约束整理为可执行规则。

### 4.1 三个设计拨盘

默认作为内部判断基线：
- `DESIGN_VARIANCE = 8`：结构不走最保守对称模板
- `MOTION_INTENSITY = 6`：动效有存在感，但不做满屏表演
- `VISUAL_DENSITY = 4`：默认中低密度，留足呼吸感

使用方式：
- 用户明确要求“极简 / 商务 / 稳重”时，下调变体和动效强度
- 用户明确要求“实验感 / 高级感 / 记忆点 / 杂志感”时，提高结构变化和材质表达
- 工具后台默认提高信息秩序，降低视觉噪声

### 4.2 反 AI 模板味规则

默认主动规避以下常见俗套：
- 首屏永远居中大标题 + 按钮 + 三张等宽卡片
- 紫蓝霓虹渐变 + 发光按钮
- 大面积空泛口号文案
- 三列完全对称功能卡片
- 过多圆角、阴影、玻璃拟态堆叠
- 靠“很大标题”而不是层级建立视觉重点

替代策略：
- 首页优先考虑左文右图、分屏、错位、非完全对称布局
- 功能区避免机械 3 等分，优先 2+1、不等比、交错节奏
- 记忆点优先来自一个强场景，而不是每个区块都在抢戏

### 4.3 版式规则

- 当设计变化度较高时，默认避免首屏完全居中结构。
- `md` 及以上可使用不对称布局；`md` 以下必须回落为单列安全布局。
- 容器宽度默认控制在 `max-w-[1400px]` 或 `max-w-7xl`。
- 复杂多列布局优先 `Grid`，避免复杂 `Flex` 百分比计算。
- Hero、首屏、全高区块禁止默认使用 `h-screen`，改用 `min-h-[100dvh]`。

### 4.4 排版规则

- 标题优先使用更有识别度的无衬线字体，不默认使用 `Inter`。
- 偏高级 / 创意 / 品牌感场景，优先考虑：
  - `Geist`
  - `Outfit`
  - `Cabinet Grotesk`
  - `Satoshi`
- 工具型 / SaaS / Dashboard 场景禁止使用 Serif 作为主界面字体。
- 正文宽度控制在舒适阅读区间，默认不超过 `65ch`。
- 标题层级靠字号、字重、间距、明度建立，不靠盲目放大。

### 4.5 色彩规则

- 单页面默认 **1 个主强调色**。
- 强调色饱和度受控，不追求刺眼高纯度。
- 默认禁用“AI 紫蓝发光风”。
- 灰阶基底必须统一，不在同一页面里混用冷暖灰逻辑。
- 若无品牌色，优先使用中性底色 + 单一高对比强调色。

### 4.6 卡片、材质与阴影规则

- 卡片只在“层级需要被抬起”时使用，不为装饰滥用。
- 高密度后台默认减少卡片，优先使用：
  - 分组留白
  - `border-t`
  - `divide-y`
  - 弱分隔线
- 若使用毛玻璃，不只写 `backdrop-blur`，还应补：
  - 内描边
  - 轻微内阴影
  - 受控透明度
- 阴影要轻、宽、染背景色，不用廉价黑色重阴影。

### 4.7 状态设计规则

任何可交互页面，默认补齐：
- Loading
- Empty
- Error
- Success / Active Feedback

要求：
- Loading 优先骨架屏，不优先转圈 spinner
- Error 就地提示，不藏在角落
- 表单错误文案放在输入项下方
- 按钮、卡片、Tab 需要有明确按压反馈

### 4.8 动效工程规则

- 连续动画、磁吸、跟随、布局转场，不用粗暴 `useState` 驱动高频刷新。
- 复杂持续动画要隔离到最小客户端组件中。
- 动画优先只动：
  - `transform`
  - `opacity`
- 禁止默认动：
  - `top`
  - `left`
  - `width`
  - `height`
- 滚动复杂联动优先 GSAP / ScrollTrigger，不手写原始 scroll 监听硬堆逻辑。

## 5. 页面设计标准流程

### 阶段 A：任务识别

先判断任务属于哪一类：
- 新页面生成
- 旧页面改版
- 局部区块优化
- 视觉升级
- 动效增强
- 品牌表达加强
- 工具型界面优化

### 阶段 B：上下文收集

至少明确以下信息：
- 页面目标是什么
- 面向谁
- 希望页面呈现什么气质
- 当前项目是否已有品牌与样式体系
- 使用什么技术栈
- 是否需要本地预览
- 是否允许使用 GSAP / Anime.js / Motion / Three.js
- 是否需要交付可打包产物
- 是否已有文案、图片、接口、品牌规范

### 阶段 C：设计定向

根据任务决定本次设计重点偏向：
- 转化导向
- 品牌导向
- 产品效率导向
- 叙事展示导向
- 视觉冲击导向
- 沉浸式动效导向

同时明确三件事：
- 视觉密度高还是低
- 结构保守还是变化
- 动效克制还是有表演性

### 阶段 D：实现策略确定

必须先确认：
- 是否延续现有项目结构
- 是否需要新增依赖
- 若新增依赖，先检查 `package.json`，不能想当然直接引用
- 是用原生实现、组件动效、时间线动效，还是 3D 特效

### 阶段 E：skill 选择

推荐职责分工：
- 审美与结构增强：`design-taste-frontend`
- 页面结构与实现：`frontend-design`
- 工作流、拆解、验证：`superpowers`
- 整体设计质量评审与收口：`impeccable`（按 `critique / audit / polish / harden / adapt` 等子命令调用）
- 滚动叙事与复杂编排：`gsap-*`（按 `gsap-core / gsap-timeline / gsap-scrolltrigger / gsap-react / gsap-performance` 路由）

### 阶段 F：实现与迭代

默认按以下顺序推进：
1. 先搭页面骨架
2. 再做层级、版式、视觉系统
3. 再补状态与反馈
4. 再引入动效
5. 再做响应式和触控适配
6. 最后做性能收口和文档更新

### 阶段 G：验证与交付

交付前至少检查：
- 入口文件是否正确
- 资源路径是否正常
- 页面能否本地预览
- 响应式是否正常
- 动效是否卡顿
- 图标是否统一
- 动效库是否符合选型规则
- 修改说明是否完整

## 6. 已安装 skill 的职责分工

### 6.1 `design-taste-frontend`

作用：
- 作为默认的审美增强与前端界面规则引擎
- 负责反模板味、版式节奏、材质控制、字体与色彩校准
- 强制补齐 loading / empty / error / tactile feedback
- 对高质量前端界面提出更强工程约束

使用时机：
- 页面普通、像模板
- 结构太保守
- 配色、排版、卡片、阴影显得廉价
- 需要把“能用”升级成“更像成熟设计稿”

强制要求：
- 所有 landing page / 营销站 / 作品集 / 重设计类页面，进入最终页面实现前必须先读该 skill
- 写任何页面代码前，先产出一行 `Design Read`
- 再根据 `Design Read` 确定 `DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`
- 将 `Design Read` 与三档位结论写入 `DISCOVERY.md`

### 6.2 `impeccable`

作用：
- 这是一个**单入口 skill**，通过不同子命令覆盖设计、评审、收口、加固、响应式与动效优化
- 适合做全局界面质量判断，也适合对单个页面 / 区块执行定向优化
- 重点不是“泛用润色”，而是根据目标选择明确命令，例如：
  - `impeccable critique`：设计评审、启发式打分、找优先问题
  - `impeccable audit`：可访问性、性能、响应式、实现质量检查
  - `impeccable polish`：交付前收口
  - `impeccable adapt`：补移动端 / Pad 适配
  - `impeccable harden`：补错误态、边界态、健壮性
  - `impeccable animate` / `colorize` / `typeset` / `layout`：做定向增强

使用时机：
- 需要先评估问题，再决定改哪里
- 多区块页面需要统一气质、节奏与层级
- 交付前需要高标准收口
- 已知问题明确，希望按维度定向处理，而不是泛泛“优化一下”

调用建议：
- 不写成笼统的 `impeccable`
- 默认写成“命令 + 目标”的形式，例如：`impeccable critique 首页 Hero`、`impeccable polish 结算页`

### 6.3 `frontend-design`

作用：
- 把设计意图落实为页面结构、组件组织与前端实现方案
- 负责区块拆分、信息分层、结构落地

使用时机：
- 需要从设计方向推进到真实页面实现
- 需要梳理组件组织和结构层级

### 6.4 `superpowers`

作用：
- 提供执行纪律、规划、分步推进、验证与收口流程
- 偏工作方法，不替代视觉设计

使用时机：
- 任务较大
- 需要多阶段推进
- 需要更强验证与交付秩序

执行建议：
- 复杂或大需求先用 plan 流程规划
- 将实现拆分成多个子任务后再推进，不直接把复杂需求一次性糊成一个大改动

### 6.5 `gsap-*`

作用：
- 这是 **GSAP 官方 skills 组**，不是一个单独命令
- 用于滚动叙事、时间线编排、多元素联动、复杂转场与性能收口
- 应按任务类型路由到具体 skill，而不是只写 `gsap-*`

适用场景：
- 滚动叙事
- 复杂时间线动画
- 多元素联动
- 强节奏展示页

推荐路由：
- `gsap-core`：基础 tween、easing、transform / opacity 动画
- `gsap-timeline`：多步骤编排、时间线控制
- `gsap-scrolltrigger`：滚动驱动、pin、scrub、分段触发
- `gsap-react`：React / Next 场景下的生命周期、作用域与清理
- `gsap-performance`：性能收口、避免卡顿、降级建议
- `gsap-plugins` / `gsap-utils`：确有插件或工具函数需求时再补用

## 7. 常见任务下的 skill 串联方式

### 场景一：从零生成 Landing Page

推荐顺序：
1. `superpowers`：理清需求、阶段与验证点
2. `design-taste-frontend`：确定结构调性与审美规则
3. `frontend-design`：把结构与区块落到真实页面方案
4. `impeccable critique` 或 `impeccable polish`：做整体质量校正与收口
5. 需要动效时，再按场景接 `Anime.js / Motion / gsap-*`

### 场景二：现有页面太普通，需要高级感

推荐顺序：
1. `design-taste-frontend`
2. `impeccable critique`：先找出“普通感”来自结构、排版还是配色
3. 再按问题选择：`impeccable layout / typeset / colorize / polish`
4. 需要落代码结构调整时，再接 `frontend-design`

### 场景三：首页需要滚动叙事与强动效

推荐顺序：
1. `design-taste-frontend`：先定视觉秩序和版式
2. `gsap-core`：先定基础动画属性与 easing
3. `gsap-timeline`：编排段落节奏
4. `gsap-scrolltrigger`：接滚动驱动
5. React 项目补 `gsap-react`
6. 最后 `gsap-performance`

### 场景四：仪表盘 / 工具型后台界面

推荐顺序：
1. `superpowers`
2. `frontend-design`
3. `design-taste-frontend`
4. 必要时补 `Motion`
5. 交付前优先 `impeccable audit`
6. 最后 `impeccable polish` 或 `impeccable harden`

### 场景五：品牌页需要特效与记忆点

推荐顺序：
1. `design-taste-frontend`
2. `impeccable critique`：先确认记忆点该落在 Hero、转场还是内容切换
3. 场景判断后选择：`Anime.js / Motion / gsap-* / Three.js`
4. 若用 GSAP，按 `core → timeline / scrolltrigger → react → performance` 路由
5. 最后做性能与降级验证

## 8. 动效与特效技术选型规则

### 8.1 Anime.js

适合：
- 轻量级页面动效
- 文案、按钮、卡片、区块入场
- Loading、hover、列表过渡、小型强调

优先条件：
- 目标是更灵动、更精致
- 不涉及复杂 3D
- 不涉及重滚动叙事
- 不需要复杂时间线控制

### 8.2 Motion

适合：
- 组件级交互动画
- 页面状态切换
- layout transition
- React 场景中的现代 UI 动效

优先条件：
- 页面偏产品化
- 需要组件级状态反馈
- 需要更丝滑的声明式交互体验

### 8.3 GSAP

适合：
- 滚动驱动动画
- 强控制力时间线
- 多元素联动演出
- 复杂叙事型 Hero

优先条件：
- 需要滚动叙事
- 需要复杂编排
- 需要高控制力

默认路由：
- 基础补间先看 `gsap-core`
- 时间线编排看 `gsap-timeline`
- 滚动驱动看 `gsap-scrolltrigger`
- React / Next 生命周期与 cleanup 看 `gsap-react`
- 收口优化看 `gsap-performance`

### 8.4 Three.js

适合：
- 3D Hero 场景
- 粒子、空间、材质、光效
- 特效本身是核心记忆点的页面

优先条件：
- 特效是亮点而非点缀
- 有足够性能预算
- 能接受更高开发复杂度
- 已设计好降级策略

### 8.5 硬规则

1. 普通 UI 入场、小交互、小范围强调：优先 `Anime.js`
2. React 组件交互与状态动画：优先 `Motion`
3. 滚动驱动、时间线编排、叙事动画：优先 `GSAP`，并按 `gsap-core / gsap-timeline / gsap-scrolltrigger / gsap-react / gsap-performance` 分工
4. 3D 场景、粒子、空间视觉、沉浸式特效：优先 `Three.js`
5. 单页不无原则混用过多动画库
6. React 项目里使用 GSAP 时，默认补看 `gsap-react`，确保作用域与 cleanup 正确
7. 同一组件树内，避免把 GSAP / Three 与组件级 Motion 胡乱混在一起
8. 大滚动场景上线前，默认补看 `gsap-performance`
9. 所有酷炫效果必须让位于：
   - 可读性
   - 性能
   - 响应式
   - 交互清晰度

## 9. 页面类型专用规则

### 9.1 登录页 / 表单页

- 优先保证可读性、可输入性、状态反馈清晰。
- Label 放在输入框上方。
- Error 文案放在输入项下方。
- 不允许为了视觉效果牺牲表单可用性。
- 默认不使用过重 3D 特效。
- 高级感主要来自：排版、留白、层次、边界处理、状态反馈。

### 9.2 官网 / Landing Page

- 首屏必须有明确视觉焦点。
- 文案层级必须在 3 秒内能被读懂。
- 避免“居中大标题 + 三卡片”默认模板。
- 记忆点优先放在 Hero、转场、关键内容切换处。
- 动效是强化叙事，不是掩盖内容空洞。

### 9.3 Dashboard / 工具后台

- 优先保证信息清晰、操作路径短、反馈及时。
- 减少无意义卡片包装。
- 高密度时依靠分隔、网格和留白组织信息。
- 动效只用于反馈状态、切换层级和局部引导。
- 高级感来自秩序、比例、统一细节，而不是炫光背景。

### 9.4 展示 / 品牌 / 叙事页

- 允许更强的视觉戏剧性，但仍要控节奏。
- 重点打造 1 个强记忆场景，不追求全页处处高潮。
- 可引入 GSAP 或 Three.js，但必须附带移动端降级策略。

## 10. 页面类型方案模板

以下模板用于出方案阶段的快速落稿，重点是减少遗漏，不是强制每个项目都长得一样。

### 10.1 Landing Page 方案模板

1. 页面类型 / 目标
   - 单页转化型 Landing，目标是让用户在首屏 3 秒内理解价值，并完成注册 / 留资 / 咨询。
2. 目标用户 / 使用场景
   - 首次访问用户，以移动端和桌面浏览为主，决策时间短，需要快速建立信任。
3. 主要板块与信息层级
   - Hero
   - 核心卖点
   - 场景 / 功能说明
   - 社会证明 / 案例
   - FAQ
   - CTA 收口
4. 设计拨盘
   - `DESIGN_VARIANCE = 6-8`
   - `MOTION_INTENSITY = 4-6`
   - `VISUAL_DENSITY = 3-4`
5. 配色 / 字体 / 图标
   - 中性底色 + 1 个主强调色
   - 标题使用更有识别度的无衬线
   - 图标默认 Lucide
6. 素材 / 文案 / 接口
   - 用户提供文案优先；无文案时先做结构占位并标明待补
   - 若有表单提交，默认考虑本地代理或 mock
7. 技术实现
   - 优先原生或延续现有项目技术栈
   - 动效先用 CSS / Anime.js；滚动叙事再升级 GSAP
8. 状态设计
   - 表单提交 `loading / success / error`
   - 无案例或无 FAQ 时给安全降级文案
9. 响应式策略
   - H5 首屏先露出标题、价值点、主 CTA
   - Pad 保持两段式信息组织，避免桌面布局硬缩
   - 触屏 hover 信息改默认可见或点击展开
10. 风险 / 待确认
   - 核心文案是否已定稿
   - 是否有真实案例、Logo、数据可用

### 10.2 Dashboard / 工具后台方案模板

1. 页面类型 / 目标
   - 工具型后台页面，目标是让用户快速读状态、完成操作、减少误判。
2. 目标用户 / 使用场景
   - 高频使用的熟练用户，桌面优先，但 Pad 也需可操作。
3. 主要板块与信息层级
   - 顶部状态摘要
   - 筛选 / 操作区
   - 主内容区：表格 / 列表 / 图表
   - 侧边详情或二级面板
4. 设计拨盘
   - `DESIGN_VARIANCE = 4-6`
   - `MOTION_INTENSITY = 2-4`
   - `VISUAL_DENSITY = 6-8`
5. 配色 / 字体 / 图标
   - 中性灰阶统一，强调色只承担状态提示或主操作
   - 主界面不用 Serif
   - 数字密集区可搭配等宽数字
6. 素材 / 文案 / 接口
   - 优先读取真实字段与状态枚举
   - 接口未就绪时先定义 mock 数据结构
7. 技术实现
   - 延续现有组件系统和状态管理
   - 组件交互动画优先 Motion；无需为后台引入重滚动特效
8. 状态设计
   - 列表 `loading / empty / error`
   - 操作按钮有 `pending / success / failure`
   - 过滤条件、分页、无权限、无结果要有反馈
9. 响应式策略
   - Pad 竖屏优先改为分段堆叠，而不是硬保多栏
   - 触屏主操作区按钮热区不小于 `44 x 44px`
   - 横向表格必要时允许局部横滚，但主操作列应优先保留
10. 风险 / 待确认
   - 哪些字段是主决策信息
   - 哪些操作高风险，需要二次确认或撤销

### 10.3 登录 / 表单页方案模板

1. 页面类型 / 目标
   - 登录 / 注册 / 提交表单页，目标是低阻力完成输入与提交。
2. 目标用户 / 使用场景
   - 新用户或回访用户，常见于移动端单手操作与桌面快速录入。
3. 主要板块与信息层级
   - 标题与说明
   - 表单主体
   - 辅助说明 / 帮助入口
   - 次级操作：忘记密码、切换登录方式、返回
4. 设计拨盘
   - `DESIGN_VARIANCE = 3-5`
   - `MOTION_INTENSITY = 1-3`
   - `VISUAL_DENSITY = 4-5`
5. 配色 / 字体 / 图标
   - 保证对比度和可读性优先
   - 图标只辅助输入语义，不承担核心说明
6. 素材 / 文案 / 接口
   - 错误文案、校验规则、接口返回码需要尽量明确
7. 技术实现
   - 先保证原生可提交与校验反馈
   - 视觉动效只做轻反馈，不做重表演
8. 状态设计
   - 字段级错误
   - 提交中
   - 提交失败
   - 提交成功 / 下一步引导
9. 响应式策略
   - H5 默认单列，主按钮固定清晰可见
   - hover 信息一律改为常驻提示或点击查看
10. 风险 / 待确认
   - 校验规则是否完整
   - 成功后的跳转与失败后的重试策略是否明确

## 11. 响应式与设备适配规则

页面方案必须明确：
- 主要断点策略
- 触控热区策略
- Pad 横竖屏处理
- H5 首屏信息优先级
- Hover 在触屏设备上的替代方式

默认要求：
- PC / Pad / H5 都可用
- `md` 以下优先安全单列布局
- 触屏设备不依赖 hover 才能完成核心操作
- 首屏核心信息在 H5 中优先露出，不被装饰内容挤掉
- 触控热区足够大，按钮与卡片点击区域明确

推荐量化标准：
- 主要断点默认至少覆盖：
  - H5：`< 768px`
  - Pad：`768px - 1279px`
  - PC：`>= 1280px`
- 触控热区默认不小于 `44 x 44px`
- 正文默认控制在 `45ch - 65ch`，长文不超过 `75ch`
- H5 首屏默认应在不滚动时露出：
  - 页面标题或核心价值点
  - 1 个主 CTA 或主要操作入口
  - 关键首图或关键状态，不允许三者同时被装饰内容挤出首屏
- 触屏设备上的 hover 替代方式必须落到真实交互：
  - 改为点击展开
  - 改为默认可见
  - 改为首层直接展示关键操作
- Pad 横竖屏都要验证：
  - 横屏不出现内容稀疏到失衡
  - 竖屏不出现桌面布局硬缩放、横向滚动或点击拥挤

图片校验与交付要求：
- 外链真实图至少校验返回 `200` 且 `content-type` 为 `image/*`
- 预览中确认图片实际加载成功，不允许破图交付
- 若暂时无法可靠自动核对贴题性，在 `ASSETS.md` 标记“待人工核对”，并在预览时提醒用户确认

## 12. 禁止项与降级规则

### 12.1 默认禁止项

- 不默认混用多套 icon 库
- 不默认同时混用多套动画引擎
- 不为了“酷炫”引入明显拖慢页面的背景特效
- 不使用泛滥玻璃、泛滥阴影、泛滥渐变
- 不使用无意义三列等宽卡片功能区
- 不使用与页面目标无关的 3D 特效
- 不在移动端默认保留桌面级重动效
- 不默认使用 `Inter` 作为所有项目的审美安全答案
- 不默认使用紫蓝霓虹 AI 风

### 12.2 降级规则

- 表单、转化、功能操作页面：视觉特效优先降级，交互清晰度优先
- 移动端性能不足：优先关闭粒子、模糊、复杂时间线、大面积视差
- 页面信息层级已足够强时：不再额外堆叠动画
- 外部库引入成本高于效果收益时：优先回退到原生 CSS / JS 动画
- 连续动画影响电量或滚动表现时：优先减少数量与频率

## 13. 页面交付前检查清单

交付前默认检查：
- 页面入口是否正常
- 静态资源是否正确引用
- 本地预览是否可运行
- 主要断点下布局是否正常
- PC / Pad / H5 是否都能使用
- 文字可读性是否足够
- 图标是否统一为 Lucide 或项目既有图标体系
- Loading / Empty / Error / Active 状态是否齐全
- 动效是否与场景匹配
- 动画库是否选型正确
- 页面是否因特效牺牲性能
- 是否有必要的降级处理
- 是否说明了实现取舍与假设
- 是否存在明显 AI 模板味

建议补充为硬性验收项：
- 至少完成一次真实运行验证：本地预览、构建、或页面截图检查，而不是只看代码
- 主流程涉及交互时，必须验证 `Loading / Empty / Error / Active` 至少 4 类状态
- 主要交互元素必须验证键盘可达、可见焦点、可点击反馈
- 触屏主操作默认不依赖 hover 才能完成
- 若使用动画：
  - 主要动画不依赖 `top / left / width / height`
  - 有移动端降级或 `prefers-reduced-motion` 处理
- 若使用外部动效库：
  - 已说明为什么不用原生 CSS / JS 即可解决
  - 已说明为什么该库比同页其他方案更合适
- 若页面为阅读型或营销型：
  - 首屏 3 秒内能读懂核心价值点
  - 主 CTA 在首屏或首屏后一屏内明确可见
- 若页面为表单 / 后台 / 工具型：
  - 主要任务路径不依赖装饰性动效
  - 错误提示在控件附近可见，不藏在页面角落
