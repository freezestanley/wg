# webgen 页面设计指南

> 目的：为 `webgen` agent 提供统一的页面设计、前端审美、动效选型与 skill 协同流程。该文档用于指导 `webgen` 在生成或迭代网页时，如何稳定调用已安装能力、遵循统一约束，并输出可运行、可预览、可交付的页面结果。

## 0. 使用方式

- 需要快速判断任务方向时，先看：`docs/webgen-design-cheatsheet.md`
- 需要完整规则、约束、流程、选型依据时，再看本文
- 默认顺序：`AGENTS.md` → `docs/webgen-design-cheatsheet.md` → `docs/webgen-design-guide.md`

### 0.1 规则优先级

当多份规则出现交叉或冲突时，按以下优先级执行：
1. `AGENTS.md` 硬约束
2. 当前项目自己的约束、品牌规范、组件规范、接口约束
3. 本文档 `docs/webgen-design-guide.md`
4. 已安装 skill 的建议与偏好

执行原则：
- 本文档只定义 `webgen` 的默认增量规则，不覆盖 `AGENTS.md`
- skill 内部若与 `webgen` 既有约束冲突，以 `AGENTS.md` 和本指南为准
- 项目已存在品牌 / 设计系统时，优先延续项目体系，不为追求“高级感”强行改风格

## 1. 文档定位

这份文档不是灵感清单，而是 `webgen` 的默认设计操作系统。

适用范围：
- 新页面生成
- 现有页面改版
- Landing Page / 官网 / 活动页
- 仪表盘 / SaaS / 工具后台
- 页面动效增强
- 品牌感、质感、审美升级

核心目标：
- 让页面结果稳定、统一、可落地
- 让设计判断不再靠临场拍脑袋
- 让 skill 分工、技术选型、交付检查可复用
- 减少“AI 模板味”“乱堆特效”“结构松散”的低质量输出

## 2. 最高优先级约束

这部分是默认硬规则。若用户没有明确提出相反要求，`webgen` 必须遵循。

### 2.1 先方案，后编码

- 必须先给出页面方案，再进入实现。
- 方案至少说明：
  - 页面目标
  - 主要板块
  - 风格方向
  - 配色 / 字体方向
  - 素材 / 接口策略
  - PC / Pad / H5 适配策略
- 用户未明确确认前，不进入页面业务代码实现。

方案默认输出模板：
1. 页面类型 / 目标
2. 目标用户 / 使用场景
3. 主要板块与信息层级
4. 风格方向与设计拨盘：`DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`
5. 配色 / 字体 / 图标方向
6. 素材 / 文案 / 接口来源与缺口
7. 技术实现与依赖策略
8. 状态设计：`Loading / Empty / Error / Active Feedback`
9. 响应式策略：断点、Pad 横竖屏、H5 首屏优先级、hover 替代
10. 风险、假设、待确认项

### 2.2 先可运行，再精修

默认推进顺序：
1. 先搭结构
2. 再定层级与视觉
3. 再补状态与交互
4. 再加动效
5. 再做响应式细化
6. 最后收口性能与细节

### 2.3 默认技术与实现立场

- 默认优先原生 HTML / CSS / JS。
- 若已有项目使用 React / Next / Vite，则优先延续，不轻易换栈。
- 页面设计必须能真实落地为可运行代码，不输出纯概念稿。
- 视觉表达必须服务页面目标，不为炫技牺牲信息传达。

### 2.4 默认图标规则

- 默认只使用 **Lucide**。
- 不混用多套图标库。
- 若 Lucide 无法满足，再说明原因后扩库。
- 图标线宽、圆角、视觉密度必须统一。

> 注：新安装的 `design-taste-frontend` skill 内部推荐 `Phosphor / Radix`，但对 `webgen` 来说，默认仍以 Lucide 为先；除非用户明确指定，或项目现有体系已固定使用其他图标库。

### 2.5 动效库选择规则

根据场景选最合适方案，不无原则混用：
- `Anime.js`
- `Motion`
- `GSAP`
- `Three.js`

补充约定：
- 当现有模板不是 React，或当前项目不适合直接引入 React 生态时，可把 `React Bits` 视为**动效参考源 / 视觉效果参考源**，用于借鉴组件效果、节奏与交互模式，再用当前技术栈复刻，不默认把它作为运行时依赖直接接入。

所有动效必须服从：
- 可读性
- 性能
- 响应式适配
- 交互清晰度
- 设备兼容与降级策略

### 2.6 默认资源策略

默认浏览器侧资源优先使用以下 CDN：
- Axios：`https://cdn.jsdelivr.net/npm/axios/dist/axios.min.js`
- Tailwind CSS：`https://cdn.tailwindcss.com`
- Lucide：`https://unpkg.com/lucide@latest`
- Web Awesome CSS：`https://ka-f.webawesome.com/webawesome@3.8.0/styles/webawesome.css`
- Web Awesome loader：`https://ka-f.webawesome.com/webawesome@3.8.0/webawesome.loader.js`
- anime.js：`https://cdn.jsdelivr.net.cn/npm/animejs/dist/bundles/anime.umd.min.js`

使用原则：
- 优先延续项目现有技术栈与资源体系
- 新建页面若无既有约束，先按以上默认资源策略落地
- 偏离默认资源策略时，要能说明是因为项目既有体系、性能、合规或用户指定，而不是随意换源或扩库

### 2.7 配图与图片素材策略

适用于需要真实配图、用户不提供素材、且明确允许去线上找图的场景。

- 设计时优先找真实图，找不到再用 SVG 占位
- 用户提供图片时优先用用户素材
- 只有在用户明确同意后，才去线上找可商用免授权图
- 默认图库源：
  - `unsplash.com`
  - `pexels.com`
  - `pixabay.com`
  - `shopify.com/stock-photos`
- 获图优先顺序：
  1. 用户提供图片或 URL
  2. 图站稳定 CDN 热链 URL
  3. 搜索页辅助获取候选
  4. 实在找不到再退化为 SVG 占位
- 每个图片 URL 上线前都必须校验可用，并确认页面预览无破图
- 所有选用图的 URL、用途、状态都要写入 `ASSETS.md`
- 若交付物依赖外网热链，交付时要说明；若要求自托管，再下载进项目资产目录并改引用

## 3. 设计总原则

### 3.1 页面设计不是“好看”，而是信息与行为设计

页面设计必须同时负责：
- 信息层级
- 可读性
- 交互反馈
- 响应式布局
- 视觉秩序
- 性能体验
- 目标转化或任务完成率

### 3.2 高级感不靠堆元素

页面需要“高级感”时，优先依靠：
- 留白
- 比例
- 排版
- 节奏
- 色彩克制
- 材质细节
- 有节制的动效

不是依靠：
- 泛滥渐变
- 泛滥阴影
- 泛滥毛玻璃
- 大量装饰图标
- 无意义数据卡片
- 夸张炫光

### 3.3 先确定页面角色，再决定视觉强度

常见页面角色：
- 转化型：强调清晰、可信、低阻力
- 品牌型：强调记忆点、气质、统一世界观
- 产品型：强调结构、反馈、信息效率
- 叙事型：强调节奏、滚动、镜头感
- 工具型：强调秩序、密度、状态可读性

不同角色决定：
- 是否允许强视觉
- 是否需要复杂动效
- 是否强调沉浸感
- 信息密度应高还是低

## 4. 基于 design-taste-frontend 与 impeccable 的增强规则

以下内容吸收了 `design-taste-frontend` 的初始蓝图方法，以及 `impeccable` 的审查与专项优化方法，并结合 `webgen` 现有约束整理为可执行规则。

### 4.1 三个设计拨盘

默认作为内部判断基线：
- `DESIGN_VARIANCE = 8`：结构不走最保守对称模板
- `MOTION_INTENSITY = 6`：动效有存在感，但不做满屏表演
- `VISUAL_DENSITY = 4`：默认中低密度，留足呼吸感

使用方式：
- 用户明确要求“极简 / 商务 / 稳重”时，下调变体和动效强度
- 用户明确要求“实验感 / 高级感 / 记忆点 / 杂志感”时，提高结构变化和材质表达
- 工具后台默认提高信息秩序，降低视觉噪声

### 4.2 反 AI 模板味规则

默认主动规避以下常见俗套：
- 首屏永远居中大标题 + 按钮 + 三张等宽卡片
- 紫蓝霓虹渐变 + 发光按钮
- 大面积空泛口号文案
- 三列完全对称功能卡片
- 过多圆角、阴影、玻璃拟态堆叠
- 靠“很大标题”而不是层级建立视觉重点

替代策略：
- 首页优先考虑左文右图、分屏、错位、非完全对称布局
- 功能区避免机械 3 等分，优先 2+1、不等比、交错节奏
- 记忆点优先来自一个强场景，而不是每个区块都在抢戏

### 4.3 版式规则

- 当设计变化度较高时，默认避免首屏完全居中结构。
- `md` 及以上可使用不对称布局；`md` 以下必须回落为单列安全布局。
- 容器宽度默认控制在 `max-w-[1400px]` 或 `max-w-7xl`。
- 复杂多列布局优先 `Grid`，避免复杂 `Flex` 百分比计算。
- Hero、首屏、全高区块禁止默认使用 `h-screen`，改用 `min-h-[100dvh]`。

### 4.4 排版规则

- 标题优先使用更有识别度的无衬线字体，不默认使用 `Inter`。
- 偏高级 / 创意 / 品牌感场景，优先考虑：
  - `Geist`
  - `Outfit`
  - `Cabinet Grotesk`
  - `Satoshi`
- 工具型 / SaaS / Dashboard 场景禁止使用 Serif 作为主界面字体。
- 正文宽度控制在舒适阅读区间，默认不超过 `65ch`。
- 标题层级靠字号、字重、间距、明度建立，不靠盲目放大。

### 4.5 色彩规则

- 单页面默认 **1 个主强调色**。
- 强调色饱和度受控，不追求刺眼高纯度。
- 默认禁用“AI 紫蓝发光风”。
- 灰阶基底必须统一，不在同一页面里混用冷暖灰逻辑。
- 若无品牌色，优先使用中性底色 + 单一高对比强调色。

### 4.6 卡片、材质与阴影规则

- 卡片只在“层级需要被抬起”时使用，不为装饰滥用。
- 高密度后台默认减少卡片，优先使用：
  - 分组留白
  - `border-t`
  - `divide-y`
  - 弱分隔线
- 若使用毛玻璃，不只写 `backdrop-blur`，还应补：
  - 内描边
  - 轻微内阴影
  - 受控透明度
- 阴影要轻、宽、染背景色，不用廉价黑色重阴影。

### 4.7 状态设计规则

任何可交互页面，默认补齐：
- Loading
- Empty
- Error
- Success / Active Feedback

要求：
- Loading 优先骨架屏，不优先转圈 spinner
- Error 就地提示，不藏在角落
- 表单错误文案放在输入项下方
- 按钮、卡片、Tab 需要有明确按压反馈

### 4.8 动效工程规则

- 连续动画、磁吸、跟随、布局转场，不用粗暴 `useState` 驱动高频刷新。
- 复杂持续动画要隔离到最小客户端组件中。
- 动画优先只动：
  - `transform`
  - `opacity`
- 禁止默认动：
  - `top`
  - `left`
  - `width`
  - `height`
- 滚动复杂联动优先 GSAP / ScrollTrigger，不手写原始 scroll 监听硬堆逻辑。

## 5. 页面设计标准流程

### 阶段 A：任务识别

先判断任务属于哪一类：
- 新页面生成
- 旧页面改版
- 局部区块优化
- 视觉升级
- 动效增强
- 品牌表达加强
- 工具型界面优化

### 阶段 B：上下文收集

至少明确以下信息：
- 页面目标是什么
- 面向谁
- 希望页面呈现什么气质
- 当前项目是否已有品牌与样式体系
- 使用什么技术栈
- 是否需要本地预览
- 是否允许使用 GSAP / Anime.js / Motion / Three.js
- 是否需要交付可打包产物
- 是否已有文案、图片、接口、品牌规范

### 阶段 C：设计定向

根据任务决定本次设计重点偏向：
- 转化导向
- 品牌导向
- 产品效率导向
- 叙事展示导向
- 视觉冲击导向
- 沉浸式动效导向

同时明确三件事：
- 视觉密度高还是低
- 结构保守还是变化
- 动效克制还是有表演性

高审美页面额外要求：
- 模板默认页必须保持 `hello world` 级空壳，不得承担默认设计示范
- 先由 `design-taste-frontend` 生成初始蓝图
- 形成一行 `Design Read`
- 明确 `DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`
- 明确 `Atmosphere Layer`：`none / subtle / signature`
- 将初始蓝图摘要写入 `DISCOVERY.md`
- 补一组“老板审版五问”结论：首屏焦点、3 秒理解、证明区可信度、内容节奏、CTA 收口

### 阶段 D：初始蓝图生成

在最终实现前，必须由 `design-taste-frontend` 先生成具有明确视觉方向的初始蓝图，至少包括：
- 页面结构到区块级布局骨架
- 首屏与关键区块层级说明
- 非对称 / 节奏化布局策略
- 气氛层策略：是否需要持续背景特效、作用范围、前后景层级
- 微交互方向与动效触发点
- PC / Pad / H5 的落地差异
- 禁止退化成模板味的实现警戒项

### 阶段 D1：老板审版五问

在进入最终实现前，至少回答清楚这五个问题：
- 首屏 3 秒内能不能看出页面主题、对象和主行为
- 页面是否只有一个主焦点，而不是多中心抢戏
- 证明区是否成立：案例 / 数据 / 规格 / 信任背书是否足够
- 内容节奏是否有松紧变化，避免一整页同构区块
- CTA 收口是否明确自然，而不是最后机械放一个按钮

这些问题的答案必须写进 `DISCOVERY.md`。提升交付设计质量的主手段，是生成前把这组结构判断做对，而不是依赖模板默认长相。
设计流程产出必须来自 `Design Read`、初始蓝图和真实页面实现，不能从模板默认页改着走。

进入设计复核前，还应做一次页面反模式检查。当前默认至少拦三类问题：
- 缺少首屏 / Hero 焦点
- 缺少证明区 / 信任区
- 缺少 CTA，或直接落回三等分卡片模板
- Hero 区块缺少价值说明，且没有首屏内主 CTA
- CTA 文案过泛，例如“了解更多 / Read more”

### 阶段 E：页面质量体检

完成初始蓝图或首版页面后，至少做一次系统质检；可使用 `audit` 等能力，至少检查：
- 可访问性
- 响应式
- 性能
- 视觉层级
- 信息节奏
- 交互反馈
- 边缘情况

### 阶段 F：精准精雕细琢

根据质检结果，按问题类型进入专项优化：
- `arrange`：修复间距与视觉节奏
- `typeset`：优化字重、字号、层级、行高与阅读体验
- `colorize`：重塑更科学、和谐的配色
- `polish`：处理最后细节微调
- `animate`：补恰到好处的交互动效
- `harden`：补边缘情况、设备兼容与稳定性

### 阶段 G：实现策略确定

必须先确认：
- 是否延续现有项目结构
- 是否需要新增依赖
- 若新增依赖，先检查 `package.json`，不能想当然直接引用
- 是用原生实现、组件动效、时间线动效，还是 3D 特效
- 若存在氛围型背景特效，必须明确它属于 `none / subtle / signature` 的哪一级，以及移动端降级方案

### 阶段 H：skill 选择

推荐职责分工：
- 初始蓝图与布局骨架：`design-taste-frontend`
- 页面体检：`audit`
- 专项优化：`arrange / typeset / colorize / polish / animate / harden`
- 风格沉淀：`teach-impeccable`（位于 `skills/impeccable` 体系内）
- 页面结构与实现：`frontend-design`
- 工作流、拆解、验证：`superpowers`
- 滚动叙事与复杂编排：`gsap-*`（按 `gsap-core / gsap-timeline / gsap-scrolltrigger / gsap-react / gsap-performance` 路由）

### 阶段 I：实现与迭代

默认按以下顺序推进：
1. 先搭页面骨架
2. 再做层级、版式、视觉系统
3. 再补状态与反馈
4. 再引入动效
5. 再做响应式和触控适配
6. 最后做性能收口和文档更新

### 阶段 J：验证与设计验收

交付前至少检查：
- 入口文件是否正确
- 资源路径是否正常
- 页面能否本地预览
- 响应式是否正常
- 动效是否卡顿
- 图标是否统一
- 动效库是否符合选型规则
- 修改说明是否完整

高审美页面额外必须完成：
- 至少完成一次页面实看设计复核，而不是只看代码
- 至少检查 PC 与 H5 视口；需要时补 Pad
- 若发现布局、排版、色彩、动效或稳健性问题，回到对应的 `arrange / typeset / colorize / polish / animate / harden` 环节继续优化
- 若用户明确要求截图验收，再用 CDP 实际访问页面并截图落盘
- 未完成页面实看设计复核，不得宣称“验证完成”
- CDP 截图验收默认关闭；只有用户明确要求截图时，才输出紧凑报告与截图文件路径，避免把大截图直接塞进对话上下文

## 6. 已安装 skill 的职责分工

### 6.1 `design-taste-frontend`

作用：
- 负责先产出初始蓝图、布局骨架、层级方案与微交互方向
- 负责反模板味实现约束、版式节奏、材质控制、字体与色彩落地规则
- 强制补齐 loading / empty / error / tactile feedback
- 对高质量前端界面提出更强工程约束

使用时机：
- 从 0 到 1 先做页面蓝图
- 页面普通、像模板，需要拉开结构与节奏
- 需要把审美方向直接落到首版 HTML / 前端布局

强制要求：
- 所有 landing page / 营销站 / 作品集 / 重设计类页面，进入最终页面实现前必须先由该 skill 输出初始蓝图
- 写任何页面代码前，先产出一行 `Design Read`
- 再根据 `Design Read` 确定 `DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY`
- 再声明 `Atmosphere Layer`：`none / subtle / signature`
- 将 `Design Read`、三档位结论、`Atmosphere Layer` 与初始蓝图摘要写入 `DISCOVERY.md`

### 6.2 `impeccable`

作用：
- 作为可选的质量体检与专项优化工具箱
- 可先用 `audit` 做专业体检，再根据问题调用 `arrange / typeset / colorize / polish / animate / harden`
- 在风格稳定后，可在其体系内使用 `teach-impeccable` 沉淀长期风格约束

使用时机：
- 初始蓝图完成后，需要系统找问题
- 页面需要按布局、排版、色彩、细节、动效、稳健性分别打磨
- 项目风格已经清晰，希望记住风格以供后续复用

强制要求：
- 高审美页面默认必须至少完成一次页面实看复核；若需要额外质检，可优先使用 `audit`
- `audit` 后不能笼统说“优化一下”，应明确进入哪个专项环节
- `teach-impeccable` 视为 `impeccable` 体系内的风格沉淀步骤，不单独脱离本流程使用

### 6.3 `frontend-design`

作用：
- 把设计意图落实为页面结构、组件组织与前端实现方案
- 负责区块拆分、信息分层、结构落地
- 负责把蓝图和优化结论转成真实前端页面代码

使用时机：
- 需要从设计蓝图推进到真实页面实现
- 需要梳理组件组织和结构层级
- 需要把设计约束落成可运行页面

### 6.4 `superpowers`

作用：
- 提供执行纪律、规划、分步推进、验证与收口流程
- 偏工作方法，不替代视觉设计

使用时机：
- 任务较大
- 需要多阶段推进
- 需要更强验证与交付秩序

执行建议：
- 复杂或大需求先用 plan 流程规划
- 将实现拆分成多个子任务后再推进，不直接把复杂需求一次性糊成一个大改动

### 6.5 `gsap-*`

作用：
- 这是 **GSAP 官方 skills 组**，不是一个单独命令
- 用于滚动叙事、时间线编排、多元素联动、复杂转场与性能收口
- 应按任务类型路由到具体 skill，而不是只写 `gsap-*`

适用场景：
- 滚动叙事
- 复杂时间线动画
- 多元素联动
- 强节奏展示页

推荐路由：
- `gsap-core`：基础 tween、easing、transform / opacity 动画
- `gsap-timeline`：多步骤编排、时间线控制
- `gsap-scrolltrigger`：滚动驱动、pin、scrub、分段触发
- `gsap-react`：React / Next 场景下的生命周期、作用域与清理
- `gsap-performance`：性能收口、避免卡顿、降级建议
- `gsap-plugins` / `gsap-utils`：确有插件或工具函数需求时再补用

### 6.6 `teach-impeccable`

作用：
- 在项目风格逐渐稳定后，记录长期有效的设计上下文与风格原则
- 让后续所有设计迭代尽量延续同一审美和品牌方向

使用时机：
- 已完成若干轮审查与优化，风格已明确
- 需要把项目的长期风格约束沉淀下来

注意：
- 它属于 `skills/impeccable` 体系内的风格记忆步骤
- 不替代初始蓝图、审查和专项优化

## 7. 常见任务下的 skill 串联方式

### 场景一：从零生成 Landing Page

推荐顺序：
1. `superpowers`：理清需求、阶段与验证点
2. `design-taste-frontend`：先出初始蓝图
3. `audit`：做页面体检
4. 按报告选择 `arrange / typeset / colorize / polish / animate / harden`
5. `frontend-design`：把结构与区块落到真实页面方案
6. 需要动效时，再按场景接 `Anime.js / Motion / gsap-*`
7. 风格稳定后，再用 `teach-impeccable`

### 场景二：现有页面太普通，需要高级感

推荐顺序：
1. `design-taste-frontend`：先重做初始蓝图或版式方向
2. `audit`：确认问题来自布局、排版、色彩还是细节
3. 再按问题选择：`arrange / typeset / colorize / polish`
4. 需要落代码结构调整时，再接 `frontend-design`
5. 风格稳定后补 `teach-impeccable`

### 场景三：首页需要滚动叙事与强动效

推荐顺序：
1. `design-taste-frontend`：先定初始蓝图与叙事节奏
2. `audit`：先检查叙事与结构风险
3. `gsap-core`：先定基础动画属性与 easing
4. `gsap-timeline`：编排段落节奏
5. `gsap-scrolltrigger`：接滚动驱动
6. React 项目补 `gsap-react`
7. 最后 `animate + gsap-performance`

### 场景四：仪表盘 / 工具型后台界面

推荐顺序：
1. `superpowers`
2. `design-taste-frontend`
3. `frontend-design`
4. 必要时补 `Motion`
5. `audit`
6. 再按问题选择 `arrange / typeset / colorize / polish / harden`

### 场景五：品牌页需要特效与记忆点

推荐顺序：
1. `design-taste-frontend`
2. `audit`
3. 根据问题先走 `arrange / typeset / colorize`
4. 场景判断后选择：`Anime.js / Motion / gsap-* / Three.js`
5. 若用 GSAP，按 `core → timeline / scrolltrigger → react → performance` 路由
6. 最后做 `polish / animate / harden`，完成页面实看设计复核；只有用户明确要截图时，再用 CDP 做截图验收

## 8. 动效与特效技术选型规则

### 8.1 Anime.js

适合：
- 轻量级页面动效
- 文案、按钮、卡片、区块入场
- Loading、hover、列表过渡、小型强调

优先条件：
- 目标是更灵动、更精致
- 不涉及复杂 3D
- 不涉及重滚动叙事
- 不需要复杂时间线控制

### 8.2 Motion

适合：
- 组件级交互动画
- 页面状态切换
- layout transition
- React 场景中的现代 UI 动效

优先条件：
- 页面偏产品化
- 需要组件级状态反馈
- 需要更丝滑的声明式交互体验

### 8.3 GSAP

适合：
- 滚动驱动动画
- 强控制力时间线
- 多元素联动演出
- 复杂叙事型 Hero

优先条件：
- 需要滚动叙事
- 需要复杂编排
- 需要高控制力

默认路由：
- 基础补间先看 `gsap-core`
- 时间线编排看 `gsap-timeline`
- 滚动驱动看 `gsap-scrolltrigger`
- React / Next 生命周期与 cleanup 看 `gsap-react`
- 收口优化看 `gsap-performance`

### 8.4 Three.js

适合：
- 3D Hero 场景
- 粒子、空间、材质、光效
- 特效本身是核心记忆点的页面

优先条件：
- 特效是亮点而非点缀
- 有足够性能预算
- 能接受更高开发复杂度
- 已设计好降级策略

### 8.5 React Bits（参考源，不默认直接接入）

定位：
- `React Bits` 更适合被视为**组件动效参考源 / 视觉效果参考源**，不是当前 `webgen` 模板体系里的默认运行时依赖。
- 当模板不是 React，或当前项目以原生 HTML / CSS / JS 为主时，可参考其效果样式与交互结构，再用现有技术栈复刻。

适合：
- 需要快速寻找更有设计感的按钮、卡片、文字显现、局部背景、hover、reveal、spotlight、magnetic 一类效果参考
- 需要为首页区块、展示模块、工具页重点操作区补一个更强记忆点
- 当前项目不是 React 模板，但希望借鉴成熟动效表现

不适用：
- 把 `React Bits` 当成当前原生模板的直接运行时依赖强塞进去
- 为了追求“更炫”复制整页重效果，破坏信息层级和性能预算
- 需要滚动叙事、复杂时间线、多段 pin / scrub 场景时

使用原则：
- 优先把 `React Bits` 当作“效果样例库”，拆解其：
  - 视觉节奏
  - 动效时序
  - hover / reveal / in-view 触发方式
  - 层次与材质表达
- 再用当前模板可接受的方案落地：
  - 简单入场、小交互：优先 CSS / `Anime.js`
  - 组件状态切换：React 项目才优先 `Motion`
  - 滚动驱动、多段编排：优先 `GSAP`
- 复刻时优先保留“效果意图”，不追求 1:1 照搬源码实现。
- 同一页面最多保留 1–2 个真正有记忆点的强效果，其余区域保持克制。
- 所有参考效果都必须经过：
  - 移动端表现检查
  - 文本可读性检查
  - 性能与降级检查

参考链接：
- `https://react-bits.nodejs.cn/get-started/index`

### 8.6 硬规则

1. 普通 UI 入场、小交互、小范围强调：优先 `Anime.js`
2. React 组件交互与状态动画：优先 `Motion`
3. 滚动驱动、时间线编排、叙事动画：优先 `GSAP`，并按 `gsap-core / gsap-timeline / gsap-scrolltrigger / gsap-react / gsap-performance` 分工
4. 3D 场景、粒子、空间视觉、沉浸式特效：优先 `Three.js`
5. 需要寻找更有设计感的组件效果、但当前模板不是 React 时：优先把 `React Bits` 当作**参考源**，再用当前技术栈复刻
6. 单页不无原则混用过多动画库
7. React 项目里使用 GSAP 时，默认补看 `gsap-react`，确保作用域与 cleanup 正确
8. 同一组件树内，避免把 GSAP / Three 与组件级 Motion 胡乱混在一起
9. 大滚动场景上线前，默认补看 `gsap-performance`
10. 所有酷炫效果必须让位于：
   - 可读性
   - 性能
   - 响应式
   - 交互清晰度

## 9. 页面类型专用规则

### 9.1 登录页 / 表单页

- 优先保证可读性、可输入性、状态反馈清晰。
- Label 放在输入框上方。
- Error 文案放在输入项下方。
- 不允许为了视觉效果牺牲表单可用性。
- 默认不使用过重 3D 特效。
- 高级感主要来自：排版、留白、层次、边界处理、状态反馈。

### 9.2 官网 / Landing Page

- 首屏必须有明确视觉焦点。
- 文案层级必须在 3 秒内能被读懂。
- 避免“居中大标题 + 三卡片”默认模板。
- 记忆点优先放在 Hero、转场、关键内容切换处。
- 动效是强化叙事，不是掩盖内容空洞。

### 9.3 Dashboard / 工具后台

- 优先保证信息清晰、操作路径短、反馈及时。
- 减少无意义卡片包装。
- 高密度时依靠分隔、网格和留白组织信息。
- 动效只用于反馈状态、切换层级和局部引导。
- 高级感来自秩序、比例、统一细节，而不是炫光背景。
- 工具型页面采用满屏设计时，默认优先使用“页面壳体固定 + 内部业务区滚动”，不要把所有滚动都压给整页。
- 聊天窗口、消息列表、表格区、侧边详情区等高频内容区，默认应有明确的独立滚动容器。
- 聊天类界面默认要求：头部固定、输入区固定、消息区独立垂直滚动。
- 满屏后台默认避免无意双重滚动；若需要局部横滚或纵滚，应让滚动边界和责任区清晰可识别。
- 满屏壳布局默认允许栏目收缩，例如侧边导航、筛选栏、详情栏可折叠，以释放更多主操作空间。
- 工具型页面中的二级内容、详情内容、补充操作，默认优先考虑抽屉、弹窗、侧滑面板等按需展开容器，而不是直接挤占主工作区。
- 按钮触发的扩展内容应优先采用“就近展开、按需关闭、不中断主任务流”的交互方式，避免让用户在满屏工作台里频繁跳页丢上下文。

### 9.4 展示 / 品牌 / 叙事页

- 允许更强的视觉戏剧性，但仍要控节奏。
- 重点打造 1 个强记忆场景，不追求全页处处高潮。
- 可引入 GSAP 或 Three.js，但必须附带移动端降级策略。

## 10. 页面类型方案模板

以下模板用于出方案阶段的快速落稿，重点是减少遗漏，不是强制每个项目都长得一样。

### 10.1 Landing Page 方案模板

1. 页面类型 / 目标
   - 单页转化型 Landing，目标是让用户在首屏 3 秒内理解价值，并完成注册 / 留资 / 咨询。
2. 目标用户 / 使用场景
   - 首次访问用户，以移动端和桌面浏览为主，决策时间短，需要快速建立信任。
3. 主要板块与信息层级
   - Hero
   - 核心卖点
   - 场景 / 功能说明
   - 社会证明 / 案例
   - FAQ
   - CTA 收口
4. 设计拨盘
   - `DESIGN_VARIANCE = 6-8`
   - `MOTION_INTENSITY = 4-6`
   - `VISUAL_DENSITY = 3-4`
5. 配色 / 字体 / 图标
   - 中性底色 + 1 个主强调色
   - 标题使用更有识别度的无衬线
   - 图标默认 Lucide
6. 素材 / 文案 / 接口
   - 用户提供文案优先；无文案时先做结构占位并标明待补
   - 若有表单提交，默认考虑本地代理或 mock
7. 技术实现
   - 优先原生或延续现有项目技术栈
   - 动效先用 CSS / Anime.js；滚动叙事再升级 GSAP
8. 状态设计
   - 表单提交 `loading / success / error`
   - 无案例或无 FAQ 时给安全降级文案
9. 响应式策略
   - H5 首屏先露出标题、价值点、主 CTA
   - Pad 保持两段式信息组织，避免桌面布局硬缩
   - 触屏 hover 信息改默认可见或点击展开
10. 风险 / 待确认
   - 核心文案是否已定稿
   - 是否有真实案例、Logo、数据可用

#### 10.1A 宣传类页面可选 Scrollytelling 交付方案

- 适用场景
  - 宣传类页面、品牌故事页、周年页、发布页、纪录片式专题页
  - 目标不是“尽快扫完信息”，而是让用户沿着一条叙事线逐步深入理解品牌、理念、产品或历程
- 叙事方式
  - 页面采用 `Scrollytelling`（滚动叙事）手法，像纪录片一样随着滚动逐章展开
  - 推荐叙事顺序：创立初心 → 设计哲学 / 方法论 → 关键作品 / 里程碑 → 当下主张 / CTA 收口
  - 每一屏只承担一个核心信息点，避免一屏同时塞满标题、说明、指标和按钮
- 技术实现
  - 默认使用 `GSAP + ScrollTrigger`
  - `GSAP` 负责时间轴、分层 reveal、pin、parallax、媒资切换
  - `ScrollTrigger` 负责滚动位置与视觉节奏绑定
  - 若只是轻量滚动进入动效，不必强上整套 Scrollytelling
- 视觉与交互要求
  - 文字、图片、图形、年份、引言等元素应沿“故事发现线”层层展开
  - 可以使用章节式分屏、pin 场景、时间轴、画册式大图切换，但必须保证主焦点单一
  - 每一章结束都要回答一个问题：用户此刻比上一屏多理解了什么
- 响应式与降级
  - H5 不强求桌面同等滚动编排，可降级为顺序堆叠 + 轻量 reveal
  - `prefers-reduced-motion` 下应取消重 pin、长时间轴和强视差，保留静态信息可读性
  - Pad 端优先保留叙事顺序，不强保桌面镜头语言
- 使用边界
  - 这是宣传类页面的可选交付方案，不是默认模板
  - 当页面首要目标是转化效率、信息检索或后台操作时，不应滥用 Scrollytelling
  - 若内容素材不足、章节逻辑不成立，宁可回退常规高质量宣传页，也不要硬做滚动叙事

可直接复用方案片段：

```text
页面采用 Scrollytelling（滚动叙事）手法，基于 GSAP + ScrollTrigger 实现。页面像一部纪录片，随着用户滚动，文字、图片、视觉元素沿着一条“故事发现线”层层展开，带领用户从创立初心进入设计哲学，再到关键里程碑，最后自然收束到 CTA。H5 端允许降级为顺序堆叠 + 轻量 reveal，避免强行保留桌面级重滚动编排。
```

### 10.2 Dashboard / 工具后台方案模板

1. 页面类型 / 目标
   - 工具型后台页面，目标是让用户快速读状态、完成操作、减少误判。
2. 目标用户 / 使用场景
   - 高频使用的熟练用户，桌面优先，但 Pad 也需可操作。
3. 主要板块与信息层级
   - 顶部状态摘要
   - 筛选 / 操作区
   - 主内容区：表格 / 列表 / 图表
   - 侧边详情或二级面板
4. 设计拨盘
   - `DESIGN_VARIANCE = 4-6`
   - `MOTION_INTENSITY = 2-4`
   - `VISUAL_DENSITY = 6-8`
5. 配色 / 字体 / 图标
   - 中性灰阶统一，强调色只承担状态提示或主操作
   - 主界面不用 Serif
   - 数字密集区可搭配等宽数字
6. 素材 / 文案 / 接口
   - 优先读取真实字段与状态枚举
   - 接口未就绪时先定义 mock 数据结构
7. 技术实现
   - 延续现有组件系统和状态管理
   - 组件交互动画优先 Motion；无需为后台引入重滚动特效
   - 满屏布局优先固定页面壳体，并为主列表区、消息区、详情区定义独立滚动容器
   - 抽屉、弹窗、侧滑面板优先承担详情查看、补充编辑、辅助操作，不轻易打断主工作流
8. 状态设计
   - 列表 `loading / empty / error`
   - 操作按钮有 `pending / success / failure`
   - 过滤条件、分页、无权限、无结果要有反馈
   - 详情打开、抽屉展开、弹窗确认、栏位收缩都要有明确状态反馈与关闭路径
9. 响应式策略
   - Pad 竖屏优先改为分段堆叠，而不是硬保多栏
   - 触屏主操作区按钮热区不小于 `44 x 44px`
   - 横向表格必要时允许局部横滚，但主操作列应优先保留
   - 侧栏、筛选栏、会话栏在空间不足时应优先折叠或转抽屉，不强行压缩主内容区
10. 风险 / 待确认
   - 哪些字段是主决策信息
   - 哪些操作高风险，需要二次确认或撤销

### 10.3 登录 / 表单页方案模板

1. 页面类型 / 目标
   - 登录 / 注册 / 提交表单页，目标是低阻力完成输入与提交。
2. 目标用户 / 使用场景
   - 新用户或回访用户，常见于移动端单手操作与桌面快速录入。
3. 主要板块与信息层级
   - 标题与说明
   - 表单主体
   - 辅助说明 / 帮助入口
   - 次级操作：忘记密码、切换登录方式、返回
4. 设计拨盘
   - `DESIGN_VARIANCE = 3-5`
   - `MOTION_INTENSITY = 1-3`
   - `VISUAL_DENSITY = 4-5`
5. 配色 / 字体 / 图标
   - 保证对比度和可读性优先
   - 图标只辅助输入语义，不承担核心说明
6. 素材 / 文案 / 接口
   - 错误文案、校验规则、接口返回码需要尽量明确
7. 技术实现
   - 先保证原生可提交与校验反馈
   - 视觉动效只做轻反馈，不做重表演
8. 状态设计
   - 字段级错误
   - 提交中
   - 提交失败
   - 提交成功 / 下一步引导
9. 响应式策略
   - H5 默认单列，主按钮固定清晰可见
   - hover 信息一律改为常驻提示或点击查看
10. 风险 / 待确认
   - 校验规则是否完整
   - 成功后的跳转与失败后的重试策略是否明确

## 11. 响应式与设备适配规则

页面方案必须明确：
- 主要断点策略
- 触控热区策略
- Pad 横竖屏处理
- H5 首屏信息优先级
- Hover 在触屏设备上的替代方式

默认要求：
- PC / Pad / H5 都可用
- `md` 以下优先安全单列布局
- 触屏设备不依赖 hover 才能完成核心操作
- 首屏核心信息在 H5 中优先露出，不被装饰内容挤掉
- 触控热区足够大，按钮与卡片点击区域明确

推荐量化标准：
- 主要断点默认至少覆盖：
  - H5：`< 768px`
  - Pad：`768px - 1279px`
  - PC：`>= 1280px`
- 触控热区默认不小于 `44 x 44px`
- 正文默认控制在 `45ch - 65ch`，长文不超过 `75ch`
- H5 首屏默认应在不滚动时露出：
  - 页面标题或核心价值点
  - 1 个主 CTA 或主要操作入口
  - 关键首图或关键状态，不允许三者同时被装饰内容挤出首屏
- 触屏设备上的 hover 替代方式必须落到真实交互：
  - 改为点击展开
  - 改为默认可见
  - 改为首层直接展示关键操作
- Pad 横竖屏都要验证：
  - 横屏不出现内容稀疏到失衡
  - 竖屏不出现桌面布局硬缩放、横向滚动或点击拥挤

图片校验与交付要求：
- 外链真实图至少校验返回 `200` 且 `content-type` 为 `image/*`
- 预览中确认图片实际加载成功，不允许破图交付
- 若暂时无法可靠自动核对贴题性，在 `ASSETS.md` 标记“待人工核对”，并在预览时提醒用户确认

## 12. 禁止项与降级规则

### 12.1 默认禁止项

- 不默认混用多套 icon 库
- 不默认同时混用多套动画引擎
- 不为了“酷炫”引入明显拖慢页面的背景特效
- 不使用泛滥玻璃、泛滥阴影、泛滥渐变
- 不使用无意义三列等宽卡片功能区
- 不使用与页面目标无关的 3D 特效
- 不在移动端默认保留桌面级重动效
- 不默认使用 `Inter` 作为所有项目的审美安全答案
- 不默认使用紫蓝霓虹 AI 风

### 12.2 降级规则

- 表单、转化、功能操作页面：视觉特效优先降级，交互清晰度优先
- 移动端性能不足：优先关闭粒子、模糊、复杂时间线、大面积视差
- 页面信息层级已足够强时：不再额外堆叠动画
- 外部库引入成本高于效果收益时：优先回退到原生 CSS / JS 动画
- 连续动画影响电量或滚动表现时：优先减少数量与频率

## 13. 页面交付前检查清单

交付前默认检查：
- 页面入口是否正常
- 静态资源是否正确引用
- 本地预览是否可运行
- 主要断点下布局是否正常
- PC / Pad / H5 是否都能使用
- 文字可读性是否足够
- 图标是否统一为 Lucide 或项目既有图标体系
- Loading / Empty / Error / Active 状态是否齐全
- 动效是否与场景匹配
- 动画库是否选型正确
- 页面是否因特效牺牲性能
- 是否有必要的降级处理
- 是否说明了实现取舍与假设
- 是否存在明显 AI 模板味

建议补充为硬性验收项：
- 至少完成一次真实运行验证：本地预览、构建、或页面实看检查，而不是只看代码
- 高审美页面必须至少完成一次页面实看设计复核；只有用户明确要求截图时，才追加 CDP 截图验收
- 高审美页面必须至少经过一次页面实看设计复核；若体检或复核未通过，必须继续优化后复验
- 若风格已经稳定，建议在 `skills/impeccable` 体系内执行 `teach-impeccable` 记住风格
- 主流程涉及交互时，必须验证 `Loading / Empty / Error / Active` 至少 4 类状态
- 主要交互元素必须验证键盘可达、可见焦点、可点击反馈
- 触屏主操作默认不依赖 hover 才能完成
- 若使用动画：
  - 主要动画不依赖 `top / left / width / height`
  - 有移动端降级或 `prefers-reduced-motion` 处理
- 若使用外部动效库：
  - 已说明为什么不用原生 CSS / JS 即可解决
  - 已说明为什么该库比同页其他方案更合适
- 若页面为阅读型或营销型：
  - 首屏 3 秒内能读懂核心价值点
  - 主 CTA 在首屏或首屏后一屏内明确可见
- 若页面为表单 / 后台 / 工具型：
  - 主要任务路径不依赖装饰性动效
  - 错误提示在控件附近可见，不藏在页面角落
